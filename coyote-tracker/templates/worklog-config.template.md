# <PROJECT-KEY> ワークログ設定

このプロジェクトのワークログ記録で使う `phase_id` / `activity_id` のリストと使い分けガイド、
カテゴリの選び方のルール、およびステータス遷移で使う具体的なツール名。
フェーズ／アクティビティは `coyote_list_phases` / `coyote_list_activities`
（バックエンドが Coyote MCP の場合）で取得して埋める。**カテゴリは一覧を書かない** — 理由は下記。
（コミット対象 — チーム共有）

## ステータス遷移（作業開始・終了）

Tracker は作業単位を必ず2つのステータス遷移で挟む。**このプロジェクトのバックエンドで
実際に呼ぶツール名**を下表に書く。共通スキルはこの遷移を抽象的にしか書かないため、
「どのツールを呼ぶか」を知っているのはこの表だけ。`.claude/coyote-tracker.config` の
`task_update_tool` / `issue_update_tool` / `status_*` と必ず一致させること。

| タイミング | 対象 | 呼ぶツール | 設定するステータス |
|---|---|---|---|
| 作業開始の瞬間（最初の読み書きより前） | タスク | `<TASK_UPDATE_TOOL>` | `<STATUS_IN_PROGRESS>` |
| 人間がイシューを指名して作業開始 | イシュー | `<ISSUE_UPDATE_TOOL>` | `<STATUS_IN_PROGRESS>` |
| ワークログがスコープを締める瞬間 | タスク＋親イシュー | `<TASK_UPDATE_TOOL>` / `<ISSUE_UPDATE_TOOL>` | `<STATUS_CLOSED>` |

- 開始側の遷移は**タスクを作成／特定した同じターン**で行う。コードを読む前、方針を書く前。
- 終了側の遷移は**ワークログを提案する同じ応答**で束ねて提案する（2回に分けない）。

## カテゴリ

**ここに一覧表を置かない。** カテゴリはプロジェクトごとに異なり、必要に応じて増えていく。
少数で固定のフェーズ／アクティビティと違い、表で列挙すると必ず陳腐化し、削除済みカテゴリの
ID が宙に浮いたまま参照され続ける（COY で実際に起きた — COY-510）。

**取得方法:** `coyote_list_categories`（project_id = このプロジェクト）を呼び、
その時点の一覧から選ぶ。

**選び方のルール:**

- カテゴリは「**システムのどの部分か**」を表す。「**どういう種類の作業か**」ではない。
  `Bug` / `Feature` / `requirement` / `バグ` / `その他` のような**種別語は使わない**。
- **汎用の受け皿を作らない。** `Development` / `Misc` に相当するカテゴリを1つ置くと、
  結局すべてがそこへ入って情報量を失う。当てはまるものが無ければ既存を広く解釈せず、
  **新しい具体的なカテゴリを提案する**。
- 1 カテゴリが **25 issue** を超えたら細分化を検討する。

**Task にカテゴリを指定しない。** タスクは親 Issue のカテゴリを継承する（作成時にカテゴリを
受け付けない）。設定すべきなのは **Issue 作成時**のカテゴリだけ。
